# Institutional sign-in and saved browser authorization

October 27, 2026 — P039. This specifies the existing browser-session approach for BU Blackboard, Piazza and Gradescope, its trust assumptions and the remaining acceptance work. It is not a claim of live institutional access or a completed security certification.

## Recommended user journey

1. In the signed-in Soma workspace, choose **Connect Blackboard**. Prioritize `https://learn.bu.edu/`, where Jeremy's primary coursework lives; add Piazza and Gradescope as separate connections afterward.
2. Soma opens a short-lived Browserbase live browser at the provider's official home page. The student enters credentials on the actual provider or institutional SSO page and completes MFA there. No Soma password form, `.env` entry, chat message or model tool receives the institutional password. Password autofill/saving must not be encouraged in this hosted browser.
3. The student finishes sign-in and returns to Soma. End the interactive session, allow context synchronization, then open a fresh collection session with the saved context. Saving a context is not successful course-access verification.
4. For Blackboard, the student discovers and selects verified courses (P050); for other providers, the current route selects exact supported course pages. Only a successful scoped read with positive account/content checks marks those pages current. Preserve unsupported-page and expired-session states honestly.
5. A future refresh reuses the saved authorization while it remains valid. If the school requires sign-in/MFA again, pause collection and ask the student to reconnect. Do not retry passwords, bypass MFA, or continuously prompt Duo approvals.
6. Disconnect ends the hosted session, deletes its saved context and removes local authorization references. If remote deletion fails, retain protected cleanup references for retry and show the failure. This removes Soma's saved access; it is not a global logout of the student's other browsers or an institution-wide session revocation.

Google remains a separate OAuth flow for selected read-only Gmail and Calendar access. Browser login is not a reason to replace that route with stored Google passwords.

## What is actually trusted

The hosted browser processes the student's login and holds authenticated cookies. Browserbase is therefore a trusted processor, not a credential-blind relay. Soma's authorized server runtime can control that browser; application code, deployed operators, server secrets and provider administration are part of the trust model. “The model does not receive passwords” must not be presented as “the platform cannot access the authenticated account.”

Browserbase documents that a context contains a Chromium user-data directory, including cookies, local storage, IndexedDB and potentially saved form data. It documents per-context encryption at rest. Do not promise that a context contains only cookies or cannot retain sensitive form data. Do not deliberately save passwords or TOTP seeds. See [Contexts](https://docs.browserbase.com/platform/browser/core-features/contexts).

Authenticated cookies can grant access without another password. Treat the entire context, its references, control links and provider key as credentials. Course-page selection is an application-enforced collection restriction; the underlying website session may have broader account permissions. It is not a provider-issued read-only token.

If a user requires credentials and browser state to remain entirely on their own device, use a separately designed local companion/extension or the manual-import fallback. Cloud contexts cannot satisfy that requirement. A local companion is not implemented and is not added to P0 by this document.

## P050–P051 — Lightweight Blackboard navigation, October 27

Blackboard now discovers actual course metadata from the student's saved, independently signed-in BU context. The student selects courses and optionally maps an existing Soma course. Discovery creates no teaching facts or model job. Selected text collection uses exact application-authored authenticated GET routes for course contents, supported folders/lesson containers and announcements. It does not render the complete Ultra frontend or grant a model a browser handle. The observed UI frontend attempted a preference PUT; the collector blocks writes and uses the bounded read adapter instead.

The adapter retains owner/workspace-generation checks, an exclusive connection lease, institutional account identity binding, source-version publication guards, encrypted context references and fresh browser sessions. Reconnect invalidates the catalog. Historical material anchors its original course mapping even after deselection. Deselection, withdrawal and failed reads retain observations and mark affected lessons stale. No passwords, cookies, live-control URLs or page bodies enter public fixtures or audit narratives.

Each material slice reads at most four API pages and forty text observations within the runner's eighty-second wall budget. A resumable per-course traversal rotates to the next selected course after each slice; a course-specific unsupported read does not block later courses. Positive pagination metadata is required before a supported walk can finish and withdraw missing observations. Files, PDF/image bodies, embedded tools and external links are not fetched; an honest unsupported/partial notice remains. The 2 MiB JSON bound applies before parsing/persistence; Playwright itself buffers the response, so this is not a hard network-transfer memory limit.

The existing twenty-four-start daily provider budget remains. Scheduled Blackboard reads have a minimum ninety-minute interval, leaving nominal headroom for manual/login/discovery starts. A larger selection or multi-slice course takes longer than six hours to revisit. Course count is not limited to five. A successful slice reports its actual scope; it does not label every selected source current. Browser charges remain separate from Meta usage. Subsequent preparation uses the existing audited, budgeted selected-source pipeline; course discovery and navigation make no model calls.

**Observed live proof:** user-entered BU login/MFA and manual course opening; fresh-context course discovery; one authorized BI 107 text check extracted sixteen items with more folders pending, zero model calls and zero material publication in that probe. This proves neither complete-semester ingestion nor course-fit/teaching quality. Actual expiry/deletion, PDF/image extraction, full selected-course background publication and the real-course learning loop remain acceptance work. Synthetic and managed verification results are recorded in the build log.

**Next source sequence (P051):** validate Gradescope first because the student says most assignments are there, then Piazza for the additional class. Each uses a separate login/context, explicit source selection and provider-specific read-only verification. Their existing exact-page entry points are not evidence that automatic discovery, assignment extraction or returned-work access has passed.

## P052 — Hosted browser packaging verification

A selected-semester live check exposed a deployment-only import failure before any provider content read. Isolating the actual Vercel function file map reproduced the missing `playwright-core/browsers.json` registry; a complete local `node_modules` directory had hidden it. The three browser-reading API routes explicitly include that required asset. CI now imports the browser package from an isolated production trace, outside the checkout with no provider environment or module fallback. Removing the manifest from a temporary trace reproduces the failure.

The artifact checker also rejects dotenv/service-account paths before copying them. Vercel's local framework builder independently adds root dotenv files to its shared function layer, even when Next's route traces exclude them. Therefore do not deploy a prebuilt artifact from a developer checkout containing `.env.local`. Source deployments retain `.vercelignore`'s `.env*` exclusion; validate any prebuilt deployment from a clean staging build containing no root dotenv files. Do not move the student's active env file to work around the gate. This local packaging finding is not evidence that a secret was exposed publicly. Browser diagnostics record fixed phase/error-type facts only, never raw provider exceptions or control addresses.

## P054 — Gradescope metadata reader, October 27

The user completed Gradescope sign-in in its separate hosted context. A new bounded session then verified the enrolled catalog, explicit semester labels and all three Fall 2026 course overviews: twenty-six assignment rows. These access probes made zero model calls and did not publish material. This is provider-specific access evidence, not proof of returned-work extraction or instructional fit.

Gradescope refresh now reads only the reviewed, server-rendered assignment table: assignment name, linked numeric assignment identity when available, and displayed release/due dates with the displayed date header/timezone retained. An assignment-name button is read without clicking it or inspecting its action payload; its assignment identity remains explicitly unknown. Submission URL suffixes are discarded. Scores, submission status, answers, feedback and returned-work files are not read by this path. Dates remain source text rather than an invented conversion. Unknown table shapes fail closed. The reader validates the exact selected course, positive authenticated navigation, bounded rows and bounded final source size. Network policy allows only exact selected course documents; scripts, assets, frames, APIs and writes remain blocked.

The existing exact-page form maps selected course overviews to owned Soma courses. Automatic catalog extraction is tested as a private service helper; a student-facing Gradescope course picker has not been added. The former five-page selection ceiling is removed. Each refresh reads at most four selected pages and persists a rotation cursor, which does not change authorization scope or reset worker scheduling. The existing six-hour default means larger selections take multiple passes; no six-hour full-catalog freshness claim follows. The bounded request body and 1,000-target sanity ceiling remain operational safeguards. Unsupported overviews retain stale observations while supported pages in the same batch can publish. Global authentication, authorization and deadline failures still withhold interrupted batches. Unavailable sources also stale dependent lessons, preserving original attempts and assistance.

Versioned ingestion, owner/workspace publication guards, source auditing and the existing preparation budget remain unchanged. Routine assignment sync does not establish R9 image/PDF interpretation. Actual account expiry, provider-context deletion and the returned-work learning loop remain separate verification gates. Piazza still requires its own sign-in and read verification.
