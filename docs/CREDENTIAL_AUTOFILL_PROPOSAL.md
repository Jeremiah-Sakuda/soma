# Optional institutional credential autofill

October 28, 2026 — P071 design, P072 implementation. **Vault and isolated autofill code are implemented and synthetically verified; production activation and actual BU autofill remain unpassed gates.** No institutional password has been stored, and no KMS key or new IAM grant has been created. Automatic approval review blocked Cloud KMS activation pending explicit infrastructure approval. The currently enabled flow remains human sign-in/MFA plus encrypted saved browser authorization. See [deployment and acceptance gates](CREDENTIAL_AUTOFILL_DEPLOYMENT.md) and [browser authentication](BROWSER_AUTHENTICATION.md).

Implementation uses a dedicated private GCS vault bucket with generation-pinned updates rather than adding credential payloads to the source database. The login service has no Firebase administrative credential; a fixed authenticated app callback rechecks owned workspace/connection grants and account revocation. The ordinary browser retains only its existing encrypted authorization-state storage.

## What this solves

An explicitly opted-in student could let Soma fill an existing institutional password on a reviewed provider login page. This reduces repeated typing when saved authorization expires. It does not keep an institution's session alive indefinitely, repair a stale SSO request, bypass MFA or guarantee that a site accepts automated login. Start a fresh official login request before filling; never repeatedly submit a stale SAML form.

Keep Google on its existing read-only OAuth connection. Keep Blackboard, Gradescope and Piazza separate: a BU identity-provider login does not authorize copying that credential to another provider. Reusing saved browser authorization remains the default. A local password manager is an alternative for user-controlled entry, but its normal autofill does not automatically operate inside the remote browser image.

## Proposed trust and storage boundary

1. **Explicit owner opt-in.** Add an authenticated, recent-sign-in owner flow explaining where the password is processed, which provider/origins may receive it and how to forget it. Never request a password in chat or an env file. Accept no institutional password in existing source/model/job APIs.
2. **Separate vault.** Store ciphertext and a wrapped per-credential-version data key in a private vault collection, outside source documents, public projections and ordinary connection payloads. Use AES-256-GCM with fresh nonces and authenticated owner/workspace-generation/provider/origin/version bindings. Wrap data keys using a separately managed Cloud KMS key. Existing app-level environment encryption is not the new vault's trust boundary. [Google's envelope-encryption guide](https://docs.cloud.google.com/kms/docs/envelope-encryption) describes this pattern; KMS can also directly encrypt small secrets, so envelope encryption is a design choice rather than a platform requirement.
3. **Login-only identity and service.** Only a dedicated login service identity may read a selected vault record and decrypt its key. The ordinary Vercel runtime, source collectors, background preparation workers and Spark receive neither decrypt authority nor a plaintext-returning secret API. Prefer workload identity and least-privilege resource grants, following [Google's secret-management guidance](https://docs.cloud.google.com/secret-manager/docs/best-practices). Provider/control infrastructure and vault administration remain sensitive operational access.
4. **Narrow fill grant.** A recent owner action issues a short-lived, one-use fill grant bound to the current workspace/account generation, connection, isolated login session, credential version, page/origin and permitted action. Consume its nonce atomically. Recheck ownership, revocation, expiry, destination and session fence after asynchronous work and immediately before filling and submitting. A delayed old grant cannot fill a new or foreign session. Do not silently enable unattended password retries or scheduled password login. Credential submission needs a separate login permission; source collection remains read-only.
5. **Deterministic destination check.** Maintain reviewed exact HTTPS origins and form contracts per provider, including an explicitly reviewed BU identity-provider origin such as `https://shib.bu.edu`. Validate the actual top-level origin and form submission destination immediately before filling. Reject unreviewed frames, redirects, ports, lookalike hosts and arbitrary selectors/URLs supplied by a model or course page. Provider account identifiers must match the opted-in identity. Newly encountered SSO routes require review and human login, not broad hostname exceptions.
6. **Isolated secret-entry phase.** Revoke and drain ordinary browser-control handles, existing viewer/controller sockets, model tools, screenshots, tracing, recordings, input logs and general debug/CDP clients before the password enters the browser. Only the trusted fixed-action filler may retain the internal control transport it needs. The login service uses a reviewed fixed form action and returns sanitized status only. Keep this isolation through submission and credential-field clearance, then destroy the secret-entry process or establish a reviewed clean handoff before restoring collection access. An opt-out or revoke races safely with an in-progress fill. Provider challenges, CAPTCHA and MFA return control to the student; never store MFA seeds, recovery codes or approval responses.

The existing browser worker does **not** establish item 6: its shared control credential permits general CDP in login sessions. Its broad public-HTTPS egress policy also does not establish a reviewed SSO destination boundary. The proposed login runtime needs separately reviewed restrictive egress and must reject destination/form/frame changes during the fill/submit interval. These are independent review findings, not deployed protections.

Adding KMS encryption to the current worker alone would not create a credential-blind platform. The authorized decryption service and provider must handle plaintext briefly; a compromise of that service, privileged operators or provider scripts remains a risk. Removing ordinary browser handles during fill must be enforced server-side, not by hiding a UI button. Do not claim that JavaScript strings can be reliably zeroized or that cloud administrators cannot access the account. The legitimate website can write sensitive values into its own persisted state; synthetic canary checks and reviewed state handoff are required before claiming password-free snapshots.

## Lifecycle and operational rules

- Audit consent, credential version, grant issue/use/denial, reviewed destination identifier, fixed outcome and revoke/delete actions. Never audit passwords, form payloads, cookies, raw login errors, screenshots or live control addresses. Enable and review restricted KMS data-access logs without secret payloads.
- Make a wrong-password or stale-request failure stop after one bounded attempt. Show human recovery rather than looping against lockout/MFA controls.
- Separate **Disconnect saved browser access** from **Forget stored password**, and offer a combined action. Forget must fence future fills before asynchronous cleanup. It does not invalidate existing provider cookies or log out the institution. Track failed cleanup without retaining plaintext; specify how backups, ciphertext, wrapped keys and retention expire. A shared wrapping key and recoverable backups do not provide instant per-credential cryptographic erasure. Do not promise immediate irreversible deletion from backups without a verified retention design.
- Rotate wrapping keys and credential versions with tested rollback/recovery. Never reset ownership generations or revive tombstoned grants during recovery. Test loss of decrypt permission and unavailable KMS as fail-closed conditions.

## Milestones and acceptance gates

| Milestone | Evidence required before enabling it |
| --- | --- |
| V1: consent and isolated vault | Threat-model review; owner-only create/replace/forget; cross-account/CSRF/recent-auth tests; randomized nonce/AAD/version tests; no secret in responses, exports, logs, errors or model requests; KMS/IAM denial checks |
| V2: synthetic login-only worker | Dedicated fixture provider; origin/form/redirect/frame rejection; no collector/model/CDP access during fill; grant replay/expiry/session-swap/revoke races; failure/lockout/MFA handoff; browser process and secret-field lifecycle |
| V3: one opted-in real provider | User enters their password in the approved vault flow; reviewed official SSO destinations; one bounded fill and human MFA; saved authorization/readback; forget/disconnect/rotation and failure recovery verified without recording secret fields |

Do not add this to the current release acceptance as completed work. Until V1–V3 pass and the student opts in, restore a fresh protected login window and let the student enter credentials directly on the provider page. Course-source collection remains read-only and its scope does not expand with stored credentials.
