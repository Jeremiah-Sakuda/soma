# Soma — Muse ambition and judging gaps

November1,2026 · RUBRIC-20261101-01. Assessment of checkout `0ec9128` and retained evidence through PM153, against the participant guide supplied in this conversation. Recommendations only; no product changes, fresh model calls, tests or release verification. Current branch at inspection: `demo/hero-dijkstra`. The native overlay and hero journey supersede the earlier PM130 starting-point assessment.

## Verdict

Soma uses Muse substantially beyond a basic vision/chat integration. Its strongest current combination is interpreting a selected slide, mapping its graph to screen locations, displaying independently computed behavior over that source, investigating an intervention and preserving the experiment through a contextual explanation. The retained Wonder rejection/repair demonstrates real inter-model work.

The remaining weakness is the distance between this capable implementation and a surprising, generalizable model decision that a judge can observe. The project has ingredients for a strong submission; current evidence does not establish an exceptional experience on unfamiliar inputs or predict a first-place finish. A numerical score or ranking would imply calibration we do not have.

## Gaps, in order of competitive significance

### 1. The experiment decision is narrower than the ambitious pitch

At `src/lib/server/exploration.ts`, `choose_cost_probe` returns one existing edge ID. The instruction fixes the learning objective to the claim that fewer edges means lower cost and explicitly says to prefer a direct start-goal edge. The application computes the interventions and boundary.

This is genuine tool use, but the winning-looking behavior should make it clear why model judgment was needed. Choosing A–F under this prompt can look like a rule that could have selected the direct edge without inference.

**Proposed improvement:** let the question and current experiment determine the investigation objective and one of a few existing bounded actions. For example, “why was B updated but not settled?” should select a comparison of tentative versus settled states; “would the direct route ever win?” should select the cost boundary. The application validates targets, computes consequences and binds the returned explanation. Preserve explicit consent for actual parameter changes; inspecting a proposed hypothetical must not silently overwrite the current experiment.

**Evidence to seek:** same graph, two materially different natural questions, two appropriate observable choices without a fixed question-to-recording lookup. The result—not a verbose planning trace—should explain the choice.

### 2. Most of the native visual choreography is application-authored

`source-overlay-model.ts` computes rings, tags, relaxation equations, strike marks and captions from the checked trace. This is good correctness design. It also means the most visible motion does not itself show expansive model authorship.

**Proposed improvement:** give Muse control over the pedagogical selection: which checked state pair to contrast, which source region to reference, which misconception to test and which short explanation belongs to that result. Keep coordinates, arithmetic, state identity and rendering under application validation. There is no need to let a model invent executable code or calculate the graph's answer to make its role meaningful.

### 3. Verification can agree about a misread source

`explorationReviewRequest` receives source text, the proposed specification and checked facts. Its caller supplies `source.summary`, anchors, uncertainty and solver executions; the review request does not contain the original screenshot. Wonder can catch caption/trace inconsistencies yet miss a weight that Spark misread consistently in both summary and graph. A correct solver only proves the computation on its interpreted input.

**Proposed improvement:** independently re-inspect consequential ambiguous source details against a focused original-image crop where needed, using the existing bounded source-reading path or a specifically verified visual-review path. Require clarification on unresolved ambiguity. Test disagreements about weights, arrows and hidden connections before making stronger verification claims. Review of prose and deterministic computation remain separate checks.

The hero source was adjusted during development after start/goal captions were misread as node labels. That is an honest development correction and a reason to test unfamiliar source formats without cleaning them specifically for the reader.

### 4. Generality is not yet as convincing as the reference's visible range

The reference's sampled frames move between code, mechanisms and hardware sources while keeping the explanation beside the work. They show an impression of breadth; they do not establish its backend architecture or reliability. Soma's richest real-screen manipulation currently centers on graph search; the polished engine is recorded, and other subjects have explanation-only assurance.

**Proposed improvement:** verify two fresh graph layouts and one materially different explanation subject through the same entry interaction. A strong code diagram or conceptual AI explanation is sufficient for the breadth beat; it need not become a new checked numerical family. Preserve the different assurance levels. A handful of cases supports a demo claim, not universal coverage.

### 5. Responsiveness and voice still affect the impression

The retained hero service pass took24.020s for initial generation including a real review repair,12.249s for the investigation, and8.908s for the follow-up. Later native rehearsals are separate observations. PM151–PM152 records Gemini rate limiting after repeated narration requests. These facts limit claims of near-live generated explanations even when local manipulation is immediate.

**Proposed improvement:** keep direct manipulation instantaneous, reuse valid source/state, preserve the current visual while preparing a response and bound audio preparation. Capture actual end-to-end voice waits and interruption behavior in the final candidate. Use transparent wait-shortening in the video. Do not trade source quality or review for a latency number.

### 6. Submission copy has a few claims stronger than the implementation

The current script says “before any explanation reaches me, Muse Wonder checks it.” Review is conditional on enabled configuration, mode and evidence; this should describe the reviewed run rather than every possible explanation.

“Get an answer I can trust” is broad; “see why the route changes, with the calculation checked” states the useful guarantee more precisely. At the tipping point, distinguish a tie at7 from a strict direct-route win below7. The graph's tie-breaking may still choose either equal-cost route. Keep the artificial original slide and recorded engine labels.

These are wording recommendations, not script edits by this review.

## Recommended next investment

Prioritize **a question-directed visual investigation on the existing screen overlay**. This links the most compelling current presentation to a less predetermined Muse decision, improving both tooling and demo without creating another product surface.

Then prove transfer to unfamiliar sources and check consequential source-reading errors. Finish the native interaction and audio rehearsal before expanding the demo. The engine is a short creative coda; general computer control stays outside the main story unless it accomplishes a necessary, visibly useful step. Its current documentation still marks real Accessibility execution and the new multi-step provider path as unverified.

Fine-tuning would become useful only after identifying a repeatable failure and a suitable training/evaluation set. There is no evidence in this review that it is the best next use of time. Additional models, 3D modes and broad autonomous workflows should earn their place through an improvement in the same demonstrated question-to-investigation loop.
