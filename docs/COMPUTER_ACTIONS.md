# Optional computer actions (PM086, extended to approved plans)

Soma can propose and, after local approval, perform a short bounded plan in a selected macOS app. Muse proposes up to five steps toward the user's task; the user reviews and approves the whole plan once; Soma executes it step by step, re-observing the app before each step and stopping at the first mismatch. A step that sends, submits, deletes or purchases still needs its own approval when it is reached. This is separate from visual explanations and read-only course collection. The existing signed 0.3.0 download does not contain this change until a new native build is signed, notarized and published.

## Use

1. Start the new native build and open Soma once to establish its authenticated or guest session.
2. Focus the app you want to change (for example a lecture PDF open full screen in Preview) and press **Command–Shift–A**. Grant macOS Accessibility permission if requested, then try again. Soma opens a separate local control window that stays available above full-screen apps.
3. Review the app name and expandable control list. Enter a specific task, without secrets (for example "go to the next slide"), then choose **Ask Muse for a plan**.
4. Review every step: the control it presses or the field it replaces and the exact replacement text, or the navigation key it sends, and the effect Muse describes for that step. Steps flagged **Needs its own approval when reached** may send, submit, delete or purchase. Check the approval box and choose **Approve and run plan**.
5. Soma runs the steps in order with its window hidden. Before a flagged step it reappears and pauses; check the step box and choose **Run this step**, or **Don't run it** to discard the rest of the plan. **Escape** stops pending work at any time. It cannot undo a step the operating system has already accepted.
6. Review the per-step outcomes and the app. After a completed plan, **Capture this screen in Soma** ends computer control and takes one snapshot through the existing capture path, so the new slide can be explained. The snapshot is previewed in Soma as usual before anything is sent.

A task lasts two minutes and allows at most five executed steps in total, across all plans in that task; a plan can contain at most the remaining number of steps. These limits are unchanged from the single-action design. Selecting a different app requires a new task. Starting capture/Point & ask ends computer-control authority; starting computer control disables Point & ask to keep the Escape handler exclusive.

## Plan schema

The existing Spark Responses tool path (`requestMetaVisionResponse`, `muse-spark-1.3`, low reasoning effort) is called once per proposal with one strict function tool, `propose_plan`:

- `kind`: `plan`, `clarify` or `done`. `clarify` and `done` carry no steps; `done` is explicitly a model assessment requiring user verification.
- `reason`: a short summary of the plan (at most 400 characters).
- `steps`: 1–5 steps for `plan`, bounded again by the request's `maxSteps` (the task's remaining actions). Each step has `kind` (`click`, `type` or `key`), `target` (a supplied control ID, or `-1` for `key`), `text` (the full replacement value for `type`, otherwise empty), `key` (one allowlisted navigation key for `key`, otherwise empty), `effect` (at most 240 characters) and `consequential`.

The server (`checkedComputerPlan`) and the local broker (`validatePlan`) apply the same checks independently: known, unique, non-sensitive targets; `type` only into single-line text fields with bounded text and no control characters or script URLs; `click` never into text fields; `key` only from the allowlist, with no target or text. A press whose label looks like send, submit, delete, remove, purchase, pay, order, post, publish, share, upload, confirm or sign out is marked consequential locally whatever the model reported. At most one consequential step is allowed and only as the final step, so nothing runs after an external effect. Controls that look like coursework hand-in (`Turn in`, `Hand in`, `Submit assignment/quiz/exam…`) are refused outright: Soma never submits coursework or writes to connected services on its own initiative.

## Navigation keys

Preview, Keynote and many PDF viewers advance slides with the keyboard; the next-slide control is often not an Accessibility button. The plan can therefore include a `key` step limited to six unmodified navigation keys: Right, Left, Up and Down Arrow, Page Down and Page Up. Space is deliberately excluded because on macOS it activates the focused control and could press a button the user did not review. Return, Tab, Escape, characters and any chord with Command, Shift, Option or Control are not representable in the schema and are rejected by the helper. The helper refuses the step if a modifier key is physically held, builds the events from a private event source with explicit empty modifier flags, and posts them to the selected app's process only (`CGEvent.postToPid`), not to the global event stream. Arrow keys can still move a selection in a focused list, radio group or slider; the focused element is therefore part of the state fingerprint, so a focus change between approval and execution stops the plan.

## Approval and execution

The local privileged broker accepts IPC only from the exact bundled control page and its main frame. Hosted Soma content has no execution or capture bridge. The broker stores the reviewed plan and selected process; the renderer supplies only a boolean for plan approval and the exact waiting step index for a per-step approval, so it cannot substitute a plan or step.

Each click/type step is bound to the role and label the user reviewed, not to a numeric ID, because IDs can shift after earlier steps. Before **each** step the broker activates the selected app, takes a fresh native observation and requires:

1. the same process;
2. the same window identity (process, launch and focused-window title, hashed in the helper);
3. an unchanged state fingerprint (window identity, control labels, geometry, hashed current values and the focused element) relative to the last observation Soma made: the approval-time observation for step 1, and Soma's own post-step observation (after a 0.5 s settle) for later steps. This catches anything that changed between steps other than Soma's own step;
4. a still-present, still-unique control with the reviewed role and label, whose current ID the helper confirms against the role and label again before acting.

Any mismatch stops the plan before that step; the window shows which step stopped and why, which steps ran, and that nothing else was attempted. A native failure (for example a field that does not read back the exact value) also stops the plan, counts against the task bound and is reported as not confirmed. Escape, closing the window, or starting capture/Point & ask revokes the task; a step already in flight may have been accepted by macOS and the message says so.

Steps 2–5 act on a state the user did not see at approval time; that is inherent to a plan. The safeguards are the reviewed role/label binding, the continuity check against Soma's own post-step observation, the final-step-only rule for consequential presses with a second approval, and the five-step/two-minute bounds.

## Intelligence and boundaries

The model sees the explicit goal, app name, bounded sanitized Accessibility labels, `maxSteps` and up to five previous executed steps with actual native outcomes, so it can plan the next steps instead of repeating completed work. It does not receive a screenshot, existing field values, window title, password fields or a stream of computer activity. The label list is visible before sending. Labels are untrusted input, not instructions. A local Steps run this task list shows executed steps and native outcomes; this transient history is discarded on stop and is not durable learner evidence.

`/api/explore/computer` resolves existing ownership, acquires the existing shared admission slot, reserves the existing $0.35 exploration allowance, bounds the request to one 25-second call (output limit raised from 1,024 to 2,048 tokens for up to five steps; the request's computed upper bound stays far below the reservation), and settles actual usage. The response carries the actual model, one call and the actual settled cost; the UI labels it "proposal only". Unknown sent usage retains its reservation. Deletion/cancellation is rechecked after inference and settlement. No remote proposal executes an action.

The Swift helper uses macOS Accessibility, not shell scripts or arbitrary coordinates. It resolves standard enabled buttons, checkboxes, radio buttons and single-line text fields. Password/payment/authentication-looking controls, scripting/command controls and terminal/script-editor applications are excluded. Duplicate controls with the same role and label are rejected because the user could not distinguish the target in the approval preview. It bounds traversal, messaging and process time. None of the fingerprinted values leave the helper. For clicking, the pointer moves to the resolved control and AXPress is invoked. Typing replaces the exact editable field value through AXValue and reads it back locally. Keys are limited as described above. No Enter, Tab, arbitrary key chords, terminal commands or drag gestures are supported.

Outcomes are reported per step and honestly: a typed value is **value read back and confirmed**; a press is **press accepted** and a key is **key accepted**, which confirm only that macOS accepted the event. They do **not** prove that a slide changed, a network request finished or a submission completed. The UI says so. Unsupported/canvas-only applications require manual operation. Goal input is not a credential vault; enter secrets directly in the provider app.

## Verification and limits

**Executed for the plan extension (November 1, offline only):** `npm test --prefix desktop` 37/37 passed (9 computer-policy tests, 14 computer-session tests, 14 other desktop tests); `npx vitest run tests/server/computer-actions.test.ts tests/server/computer-route.test.ts` 18/18 passed; `npx tsc --noEmit` passed; `xcrun swiftc -typecheck` and `node desktop/build-native.cjs` compiled both native helpers; a permission-only call to the newly compiled helper reported `trusted:false` (no prompt, no observation). Mutation checks confirmed that disabling the fingerprint comparison or the per-step approval makes the corresponding tests fail. A headless Chromium render of the trusted control page with an original synthetic state stub verified the plan, awaiting-approval, stopped and completed views, checkbox gating and no horizontal overflow at 600px; its screenshot was visually reviewed.

Offline tests cover plan schema and length bounds, the remaining-action bound, the key allowlist (Space, Return, Tab, Escape, chords and prototype keys rejected), local consequential marking, final-step-only consequential steps, coursework refusal, stored-plan-only execution and renderer substitution, re-observation with activation before every step, stop on a change before step 1, stop on an outside change between steps, stop on a different window, ID re-resolution after earlier steps and stop when a reviewed control disappears, per-step approval with exact step index and decline, Escape during a step and while awaiting approval, native failure, capture gating and authority release, unknown-usage reservation retention, cancellation after inference and deletion during settlement.

**Not verified:** no real Accessibility observation, click, typing or key event was performed on a Mac display, and no provider call was made for the plan schema. Whether the Meta Responses endpoint accepts `maxItems` inside the strict tool schema, whether `postToPid` key events advance a full-screen Preview document, whether Preview's auto-hiding full-screen toolbar causes spurious mismatches, and whether the control window and capture behave as intended over a full-screen Space all remain human verification gates, together with the earlier ones: Accessibility permission on a clean Mac; a benign original form in a selected app; exact field replacement and readback; Escape and focus interruption; a new signed/notarized distribution. General desktop task completion, unattended operation and arbitrary-application support are not established.

**Earlier PM086 record (single action):** 13 focused server/route tests, 7 computer-policy/session tests, TypeScript typecheck, Swift typecheck and native compilation passed; a headless Chromium check verified the earlier approval form. The integrated synthetic live test verified a real Muse field-replacement proposal without executing it; that live test has been updated to the plan shape but has not been re-run.
