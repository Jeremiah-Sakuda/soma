## Credential architecture traced

Institutional passwords and MFA are entered in the actual provider/SSO page inside Browserbase. Soma has no institutional-password endpoint. Browserbase is a trusted processor holding sensitive browser state; its context can outlive a web session until deleted. The UI now discloses that before login. This is consistent with the provider's [context documentation](https://docs.browserbase.com/platform/browser/core-features/contexts), not proof of the provider's internal operations.

Google uses a separate web OAuth flow: an exact configured callback, S256 PKCE, random one-use state stored hashed with encrypted payload, and a verified Soma account. Tokens stay in server-side connection storage. Requested scopes are read-only; the application only issues the selected read requests. Disconnect removes Soma's stored authorization and invalidates publication; it does not promise to revoke every Google grant or terminate an already-issued network request. Provider-wide grant revocation is a separate operation. The token reconciliation fix follows the optional refresh-token replacement behavior in [RFC 6749 section 6](https://www.rfc-editor.org/rfc/rfc6749#section-6).

Connection secrets use AES-256-GCM with fresh nonces and authenticated owner/workspace/connection binding. Public metadata uses an allowlist. Browser context/session IDs are encrypted as credentials; OAuth secrets, CDP addresses and browser state are not workspace/model fields. The intended exception is a short-lived owner-authorized login control URL held transiently by the UI, with no-store responses and a no-referrer new tab. Synthetic browser tests verify it is absent from web storage and disappears on reload.

Firebase verifies account tokens/cookies with revocation checks; the account cookie is HttpOnly, Secure in production and SameSite=Lax. Account roots and records are owner/generation checked. Firestore's checked-in rules deny client reads/writes; Admin SDK operations enforce ownership. Workers require a private bearer capability, derive account identity from stored roots and revalidate disabled/deleted accounts before publication. A model receives selected course evidence, not connector secrets. Existing source-audit code emits fixed observations rather than provider URLs, tokens or login DOM.

Deletion now follows one sequence: reject unresolved leases → freeze the owner/generation → clean saved browser resources through a deletion-only private read → erase records → mark deletion complete. Retry retains the same frozen generation. A stale cleanup cannot erase a recreated workspace. An expired but unreleased lease must first be recovered through its connection flow rather than silently discarding possible cleanup work. Workspace deletion does not delete the Firebase sign-in account.

## Open production-security work

1. **Key custody and production rollout.** P044 implements authenticated key IDs, bounded current/previous/future readers, a compatible default writer, dry-run/transactional re-encryption and tested rollback/recovery. See [the rotation runbook](CREDENTIAL_KEY_ROTATION.md). Actual production replacement/retirement, protected recovery custody and a managed key mechanism if required remain operational gates. Do not replace the current key blindly. Rotation, revocation and recovery are separate lifecycle obligations in [OWASP's guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).
2. **Remote allocation ambiguity and abandoned contexts.** A provider can allocate a resource before its response/checkpoint is durably acknowledged. The new deletion barrier fixes the observed reconnect race, but does not solve every distributed allocation failure. Persist/reconcile allocation intent using verified provider lookup capabilities, add abandoned-context retention/cleanup and operational alerts. Current contexts are removed on successful explicit cleanup; there is no comprehensive orphan sweeper.
3. **Actual provider verification.** BU/Gradescope/Piazza SSO, expiry, recording/logging settings, saved-state contents and read-only endpoint behavior still need dedicated-account hosted checks. GET/HEAD plus known-action blocking is an application policy; the underlying browser login can have broader website permissions. Do not claim a provider-issued read-only token or zero credential access by deployed operators.
4. **Deployment privileges and incident controls.** Local configuration checks passed, but this environment uses application-default credentials and does not identify the deployed runtime service account. Its actual roles, operator access, key custody, audit access, retention and incident revocation were not independently verified. The current shared runtime can decrypt users' connection secrets by design. No zero-knowledge claim is appropriate. CSP hardening and a separate security review remain sensible before broader release.

These are engineering/operational gates, not requests for passwords or private course documents. M6 stays deferred while Jeremy reviews the synthetic experience.
