## Approved cloud changes (P073)

Use the existing `soma-meta-jerem-2026` project and `us-east1` region, without changing its billing association or the existing Vercel/Firestore/browser services:

- Enable Cloud KMS; create a dedicated software symmetric encryption key in a `soma-credentials` key ring, with a ninety-day primary-version rotation policy. Preserve old enabled versions until ciphertext has been rewrapped and verified. A key's primary-version change alone does not migrate saved ciphertext.
- Create a dedicated private `soma-meta-jerem-2026-credential-vault` bucket with uniform access, public-access prevention, no object versioning and no soft-delete retention. Vault tombstones contain no old encrypted payload. Consumed grant objects must survive the thirty-minute authorization lifetime; do not apply a shorter cleanup policy. Internal provider backup erasure is not promised.
- Create the `soma-credential-login` runtime identity. Give it encryption/decryption on this key only, conditional object read/create/overwrite access to the new bucket's `credential-vault/` prefix and the existing bucket's `browser-contexts/` prefix, and access to its dedicated control/callback secrets plus the existing browser-state encryption secret. Grant only `roles/storage.objectCreator` on the vault bucket's `credential-audit/` and `credential-grants/` prefixes: no read, delete or overwrite there, and no broader inherited object role that defeats those restrictions. Grant operators separate restricted audit-reading access. Give no vault-bucket or KMS-decrypt role to the normal app, browser worker, model or build identity. Review inherited project privileges as well as resource policies. Reuse the existing separate image-builder identity only for building/pushing the image. [Google documents object-prefix IAM conditions](https://docs.cloud.google.com/storage/docs/access-control/iam) and the [create-only role](https://docs.cloud.google.com/storage/docs/access-control/iam-roles).
- Create distinct random broker-control and authorization-callback secrets in Secret Manager. Never use institutional credentials as deployment secrets. Pin secret versions in the service revision; do not print/export the values into logs or public files. Enable restricted KMS data-access audit logging and review its access; application audit facts never include KMS plaintext or institutional credentials.
- Deploy a separate `soma-credential-login` Cloud Run service: one maximum instance, zero minimum instances, one active browser, 1 CPU / 2 GiB, request ceiling 2,100 seconds and thirty-minute session allocations. Build from the clean tracked `services/` context using `credential-runner/Dockerfile`; exclude node_modules, dotenv, local/private artifacts and source documents from uploads.
- Initially keep its Google IAM entry private for synthetic verification. P073 explicitly approved internet invocation of this one protected service after private health/IAM checks. Application control still requires the distinct private key; the login page requires a one-use capability followed by a scoped Secure/HttpOnly/SameSite cookie. This is not an anonymous control or password API.

These resources can incur cloud charges; credit eligibility has not been established by the code tests. This rollout does not authorize model spending or change the current source scopes.

## Implemented isolation and its limits

The new service exposes no general CDP, screenshots, arbitrary navigation or model endpoint. Enrollment starts a fresh empty browser; cancellation preserves the previously encrypted course-browser authorization. Authorization is rechecked after consent/publication audit awaits before saving credentials or handing off state. Credentials are submitted using a fixed internal top-level POST with bounded reviewed form tokens. Page input/submit handlers never receive the password. Redirect reposting, response reflection and secret-bearing redirects are rejected before a viewer can open. The service uses both an exact-host HTTPS proxy and explicit Playwright proxy configuration for its internal request client. After human MFA, export requires a positive Blackboard identity read and includes only secure HttpOnly Blackboard cookies; no Shibboleth cookies, localStorage, IndexedDB or Chromium profile transfers.

Bounded canary checks reject tested raw/escaped/URL/form/base64 reflections. They are not a proof against every possible encoding by a malicious provider. The legitimate provider, privileged login runtime and cloud administrators remain trusted. Encryption does not make an authorized password-decryption service credential-blind or guarantee JavaScript memory zeroization.

References: [Cloud KMS envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption), [symmetric encryption and integrity checks](https://docs.cloud.google.com/kms/docs/encrypt-decrypt), [Firebase session cookies and recent authentication](https://firebase.google.com/docs/auth/admin/manage-cookies), [BU authentication services](https://www.bu.edu/tech/services/security/iam/authentication/), [BU Duo login](https://www.bu.edu/tech/support/duo/log-in/).
